# 教师 WorkBuddy“是什么”与“做什么”阶段总结

## 文档定位

本文是教师 WorkBuddy 从“终局产品和 AI 方向讨论”进入“优先场景产品设计”的里程碑式阶段产出。

它集中回答两个前置问题：

1. **教师 WorkBuddy 是什么？**
2. **教师 WorkBuddy 做什么？**

这两个问题已经形成可以继续向下推进的产品共识。下一阶段讨论第三个问题：针对优先落地的闭环业务场景，产品方案应该如何拆解和设计。本文不描述 Agent Runtime、模型路由、Prompt、MCP、A2A 或其他技术实现细节。

本文是当前产品和架构讨论的阶段基线，不代表真实客户价值、生产接口和商业结果已经验证。

## 一、阶段结论

### 1. WorkBuddy 是什么

教师 WorkBuddy 是面向教师完整教学工作的通用 AI 工作伙伴和统一教师工作台。

它的终局形态不是 AI 工具目录、多个智能体列表或单一聊天窗口，而是：

```text
教师表达教学目标
→ WorkBuddy 组织授权上下文和证据
→ 生成可编辑的教学成果或判断草稿
→ 教师理解、修改、确认或拒绝
→ 进入既有业务对象和教学行动
→ 追踪结果并进入下一轮教学调整
```

WorkBuddy 的产品入口是统一教师工作台和主 Agent 身份。教师不需要理解或选择内部的 Agent、Skill、MCP、模型或工具。

WorkBuddy 可以在没有 ClassIn 的情况下，通过教师输入、资料上传和外部连接器完成核心工作；接入 ClassIn 后，获得更连续的课程、课堂、作业、互动和结果证据，因此 ClassIn 是上下文、执行和结果反馈增强层，而不是 WorkBuddy 成立的唯一前提。

### 2. WorkBuddy 做什么

WorkBuddy 不只是提供一组孤立的 AI 内容生成能力，而是沿教师教学循环组织三种能力层级：

| 能力层级 | 定义 | 典型输出 | 默认产品形态 |
| --- | --- | --- | --- |
| 单点能力 | 一次完成生成、识别、转换、检索、解释或检查 | 摘要、题目、转写、检查报告 | AI Tool |
| 组合能力 | 多个 Skill、业务工具和规则校验围绕一个业务对象协作 | 可编辑 Artifact、判断草稿、来源和不确定性 | AI Copilot |
| 完整业务闭环 | 从目标、证据和产物走到教师确认、业务写回和结果复查 | 业务对象变化、执行回执、复查结果 | Copilot；满足条件后才是有限 Agent |

WorkBuddy 的核心业务结果链是：

```text
作业与结果证据 → 错因分析 → 订正练习 → 学生完成与复查
备课演练证据 → 可观察反馈 → 课件/活动改进 → 再次演练对比
学情与课堂/作业证据 → 诊断假设 → 个性化干预 → 结果复查
```

“课程目标 → 课程对象”是课程生产基础链，也是当前锁定的第一条工程纵向切片。它为三条核心结果链提供目标、内容、活动和评价标准等上游结构。

## 四、四条优先工程切片

| 工程顺序 | 业务场景名称 | 要验证的产品能力 |
| ---: | --- | --- |
| 1 | 课程目标 → 课程对象 | 目标澄清、上下文、课程 Artifact、教师编辑、审批、写回、回执和评价 |
| 2 | 作业批改 → 错因分析 → 订正 | 作业数据、评分标准、错误聚类、答案保护、分层订正和二次结果证据 |
| 3 | 备课演练 → 教学改进 | 演练媒体、时间戳证据、可观察反馈、Artifact 版本和复练对比 |
| 4 | 学情诊断 → 个性化干预 | 多源证据、诊断假设、计划、逐项审批、跨对象写回、复查和撤销 |

战略优先级和工程顺序需要分开：三条核心结果链具有最高业务价值；课程目标到课程对象则作为低风险、可复用的架构和产品样板先行。

## 五、第三个问题：产品设计层与技术实现层分离

闭环业务场景的实现可以分成两层：

### 产品设计层

回答教师要完成什么、如何操作、看到什么、依据什么判断、哪些动作需要确认、什么结果才算完成。

### 技术实现层

回答 Agent 如何装配 Context、选择 Skill、调用模型和业务 Tool、保存 Run、处理失败以及完成审计和评价。

当前先完成产品设计层。产品层可以提出“需要证据引用、需要教师审批、需要可恢复、需要后台复查”等可观察要求，但不提前决定其 Runtime 或模型实现。

## 六、产品设计的十个拆解维度

每个优先闭环都应从以下十个维度进行产品设计：

| 维度 | 核心问题 | 主要产物 |
| --- | --- | --- |
| 1. 业务时刻与问题 | 教师在什么时刻遇到什么问题，当前人工方式是什么 | 场景定义、现状流程 |
| 2. 用户与业务范围 | 谁发起、影响谁、覆盖哪个课程/班级/学生和时间范围 | 角色与范围说明 |
| 3. 目标与成功结果 | 最终要改变什么业务对象，什么才算完成 | 结果链、成功标准、非目标 |
| 4. 触发与入口 | 从哪里进入，需要哪些前置条件，是主动触发还是系统建议 | 入口与触发矩阵 |
| 5. 教师操作流程 | 教师依次看什么、输入什么、修改什么、确认什么 | 主流程、分支流程、用户旅程 |
| 6. 业务对象与产物 | 输入和输出是什么，草稿如何编辑、比较、保存和复用 | 对象关系、Artifact 生命周期 |
| 7. 四类输入 | 产品逻辑、业务规则、Domain Knowledge、业务数据/API 如何参与 | 四类输入责任矩阵 |
| 8. AI 能力与 Skill 组合 | 需要哪些单点能力，如何组合，哪些步骤必须由教师判断 | 产品级 Skill 链和能力契约 |
| 9. 状态、控制与异常 | 生成中、缺信息、待确认、冲突、部分成功和失败如何处理 | 产品状态机、异常恢复矩阵 |
| 10. 写回、复查与评价 | 哪些动作产生副作用，如何审批、撤销，结果怎样回流 | 动作清单、回执、评价指标 |

## 七、四类输入的产品层含义

四类输入必须保持不同所有权，不能合并成一个无来源的 Prompt：

| 输入 | 产品层回答的问题 | 典型内容 |
| --- | --- | --- |
| 产品逻辑 | 教师应该如何完成任务，何时追问、生成、确认和恢复 | 流程、状态、默认范围、编辑方式、完成条件 |
| 业务规则 | 什么允许做、谁能做、对象怎样合法变化 | 权限、发布门槛、版本、评分和提交规则 |
| Domain Knowledge | 什么样的教学判断和产物更合理 | 课程标准、教学法、学科知识、评分量规 |
| 业务数据/API | 当前真实对象、证据和执行结果是什么 | 课程、课堂、作业、提交、消息、待办、版本和回执 |

需要特别区分：产品逻辑决定“流程怎么走”，业务规则决定“动作是否合法”，Domain Knowledge 决定“内容是否合理”，业务数据/API 决定“当前事实是什么”。

## 八、产品层 Skill 契约

产品设计不需要描述 Prompt、模型或 Agent 调度，但必须把 Skill 的可观察责任说清楚：

```text
Skill 解决什么问题
→ 在什么条件下调用
→ 需要哪些业务事实和知识
→ 输出什么可见结果
→ 输出引用什么证据
→ 哪些结果必须校验
→ 教师能修改、确认或拒绝什么
→ 能力不可用时如何降级
```

例如“错误聚类”不是“调用大模型分析错误”，而是：基于选定作业、提交和评分标准，生成带证据引用的共性错误候选；教师可以合并、拆分、修正或拒绝；未经确认的错误标签不能进入学生事实或直接生成正式订正任务。

## 九、产品设计阶段的统一交付物

每条闭环建议形成“六张图 + 四张表”：

六张图：

1. 业务结果链图；
2. 教师操作流程图；
3. 页面与信息架构图；
4. 业务对象与 Artifact 关系图；
5. 产品状态与控制流程图；
6. 结果复查与反馈回路图。

四张表：

1. 四类输入责任矩阵；
2. AI 能力与 Skill 组合表；
3. 业务规则、权限与风险表；
4. 场景状态、异常与验收指标表。

这些材料描述的是同一个产品场景的不同观察面，不是十份互相独立的需求文档。

## 十、下一阶段工作定义

下一阶段不是继续扩展零散 AI 功能，也不是先建设通用多 Agent 平台，而是：

1. 固化产品设计十维模板；
2. 用“课程目标 → 课程对象”完整填写一条产品场景卡；
3. 用“作业批改 → 错因分析 → 订正”检查学生数据、反馈和订正是否需要补充产品规则；
4. 用“备课演练 → 教学改进”检查媒体证据、版本和复练反馈是否需要新的产品结构；
5. 用“学情诊断 → 个性化干预”检查跨对象计划、审批、复查和撤销是否形成完整闭环；
6. 产品设计稳定后，再把稳定的产品契约映射到 Agent Harness 和工程 Module。

## 阶段完成标准

本阶段完成的判断标准是：

- 能用一句话解释 WorkBuddy 是什么；
- 能用一张全局地图解释 WorkBuddy 做什么；
- 能区分单点、组合和完整闭环能力；
- 能区分产品设计层和技术实现层；
- 四类输入拥有不同责任边界；
- 每条优先闭环都有明确的产品设计拆解维度；
- 未验证的生产能力、业务数据和商业结果仍保留 `SIMULATED`、`FUTURE` 或 `RECOMMENDATION` 标记。
