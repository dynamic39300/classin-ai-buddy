# ClassIn IM × AI Agent 2.0 三方案产品组合与验证策略

> **历史状态（2026-08-29）**：本文是基于 Round 0 探索形成的产品组合假设，不能再以“真实聊天证据已验证”来理解。方案组合留待事实研究通过质量 Gate 后重新检验。当前入口见 [ClassIn IM 真实沟通事实研究](../01-research/im-real-communication-fact-study/README.md)，原样版本见 [Round 0 封存包](../07-history/stage-deliverables/im-data-prestudy-round-0-20260828/README.md)。

## 0. 当前结论

2.0 不应被收敛成一条预先确定的升级路线。当前更合适的产品组合是：

1. **方案一：AI Enhanced IM**——以当前可运行 Demo 为基础继续增强；
2. **方案二：Learning Loop**——以 IM 连接能力为基座、独立重构页面和交互的零基概念原型；
3. **方案三：研究驱动的新范式候选**——不预设名称与形态，只有当行业模式与真实聊天场景共同证明其拥有不同的一等对象、核心流程和价值闭环时，才成为独立方案。

三个方案可以并行设计。它们不是版本号上的前后替代关系，也不应在不同样本和不同任务上各自证明自己。下一阶段应让三种形态处理同一批真实、脱敏的师生聊天 Episode，再比较效果。

## 1. 共同证据基础

### 1.1 产品事实与约束

- 线上 1.0 的核心连接是老师—学生单聊与老师—班级群聊；
- 当前 Demo 已经验证公开班级 Agent、隔离 Agent 私聊和教师私密 TeacherIn 的基础渠道与治理骨架；
- TeacherIn 的私密生成、教师审核、业务行动和执行回执不能被公开 Agent 体验替代；
- ClassIn 继续拥有班级、课程、作业、消息及正式业务结果；
- 当前研究方案不能静默改变现有 `LOCKED` 决策或被描述为生产事实。

### 1.2 真实场景证据

首轮场景必须从以下两类沟通中发现：

| 渠道 | 观察重点 |
|---|---|
| 老师—学生单聊 | 个体求助、上下文补充、个性化反馈、持续跟进、敏感信息和重复劳动 |
| 老师—班级群聊 | 通知与追问、共性问题、讨论参与、材料分享、群体理解和信息淹没 |

研究单位使用 `ConversationEpisode`，即围绕同一目标、问题或业务事项发生，并能判断起因、过程和结果的一段连续沟通。不得只按单条消息或关键词统计机会。

2026-08-28 已完成第一轮真实数据校准：全量扫描 8,197 个会话、819,700 条消息样本，分别分析 1,805 个单聊与 6,392 个班级群聊。数据证明了四个重要方向：

| 数据校准 | 产品含义 |
|---|---|
| 课程时间与课堂入口是单聊、群聊中命中最多的规则候选主题，但全量消息占比仅约 1.8% / 3.5%，且混有模板与非教学误判 | 作为方案一事实查询候选进入人工 Episode 复核，不能只凭旧主题排名直接定为 P0 |
| 群聊识别到 11,289 条学生教学疑问，固定样本内 41.1% 未观察到教师后续发言 | 3A Teacher Attention Radar 成为当前最强概念探针，但该比例只是注意力机会代理，不是未解决率 |
| 群聊知识答疑与作业主题合计 20,943 次多标签命中 | 3C Learning Case 可以承接少数需要持续跟进和收口的问题，并成为方案二入口 |
| 班级群同时覆盖教学、职业培训、金融、电商、兴趣与社交用途 | TeacherIn、Learning Loop 与主动 Agent 不能按“班级群”无差别启用，必须结合业务元数据、授权和教学相关度 |

原始数据的每个会话均固定抽取 100 条，且单聊角色全部标记为“其他”。因此本轮适合校准内容结构，不适合推断全站消息量、自然日趋势，也不能把 1v1 结论直接写成老师—学生单聊事实。完整方法和边界见[《ClassIn IM 2026 年 8 月单聊与班级群聊内容抽样分析》](../01-research/source-notes/classin_im_chat_content_sample_analysis_20260828.md)。

2026-08-28 二次回溯确认：原主题比例是“规则命中消息 / 教学锚点消息”，不是主题发生率或会话占比；长课后反馈和非教学文本可能同时命中多个主题。方案优先级必须等待人工上下文复核，当前主题表只作为候选样本导航。

### 1.3 评价原则

“高频”只能说明入口足够大，不能单独决定优先级。候选场景还需要同时满足：

- 老师负担或学生影响明显；
- 当前存在未解决、重复、遗漏、延迟或难以收口；
- AI 相比普通规则和快捷操作具有独特增益；
- 数据、权限和结果可验证；
- 失败不会破坏自然沟通或伤害学生；
- 能观察到教学或学习结果，而不只是生成更多内容。

详细编码与评分方法见[《ClassIn IM 真实聊天场景发现与 AI 机会分析框架》](../01-research/source-notes/classin_im_chat_scenario_discovery_framework_20260828.md)。

## 2. 三方案的根本差异

| 维度 | 方案一：AI Enhanced IM | 方案二：Learning Loop | 方案三候选：Learning Signal Network |
|---|---|---|---|
| 一等对象 | Conversation / Message | Learning Loop / Moment / Evidence | Learning Signal / Case / Intervention |
| 用户首先看到 | 会话、消息和当前聊天 | 今天需要推进的学习循环 | 跨会话需要判断和行动的教学信号 |
| IM 的角色 | 主产品形态 | 连接和自然表达基座 | 原始信号源与行动回流渠道 |
| AI 的主要位置 | 输入区、消息流、Agent 私聊、TeacherIn 辅助区 | Loop 的幕后编排者与受授权促进者 | 持续但低打扰的观察、分流和行动建议层 |
| 默认主动性 | 被调用为主，局部私密建议 | 围绕 Loop 目标持续促进 | 静默发现和私密分流为主，公开行动需授权 |
| 最适合 | 原流程有效，只缺检索、摘要、生成、答疑或快捷行动 | 问题需要目标、参与、活动、证据和收口 | 问题散落于大量会话，老师首先缺少发现、优先级与跨场景跟进 |
| 主要优势 | 迁移成本低、学习成本低、能渐进上线 | 能直接围绕学习结果设计完整体验 | 保留聊天低门槛，同时重新组织老师的注意力与行动 |
| 主要风险 | AI 功能叠加但产品价值仍停留在“多一个助手” | 概念和页面复杂度高，容易过度结构化自然沟通 | 误判与监控感；若只做摘要收件箱则不足以成为独立方案 |
| 当前成熟度 | 已有可运行 Demo | 产品方向确认，待独立概念原型 | 研究假设，尚未确认是最终方案三 |

其中 `Learning Signal Network` 只是目前最值得验证的方案三工作假设，不是已经确认的产品命名或范围。

## 3. 方案一：AI Enhanced IM

### 3.1 产品定义

保留用户熟悉的会话列表、群聊、私聊和输入框，在自然沟通路径中加入 AI 理解、生成和受控行动能力。

```text
Conversation
→ AI 读取当前授权上下文
→ 回答 / 摘要 / 草稿 / 建议 / 生成内容
→ 用户审核或继续追问
→ 结果留在聊天或写回业务对象
```

### 3.2 应继续强化的六层体验

1. **阅读层**：未读内容摘要、问题聚类、决定与待办提取、自然语言检索，并允许回到来源；
2. **表达层**：上下文相关的回复草稿、语气和长度调整、缺失信息提示；
3. **调用层**：普通成员与 Agent 的清晰发现、稳定身份、群内 `@`、隔离私聊及会话续接；
4. **协作层**：Agent 可以被明确加入群聊或任务，但默认不把每一次分析都公开发言；
5. **行动层**：交互式 Action、教师预览、权限复核、审批、执行和 Receipt；
6. **治理层**：数据范围、引用来源、谁能看、谁能调用、谁能部署、暂停和移除均可理解。

### 3.3 适合优先验证的场景

- 学生单聊问题缺少课程/作业上下文时，协助老师补全并生成可编辑回复；
- 群聊中同一事务被重复询问时，给老师私密摘要和统一回复草稿；
- 老师错过长聊天后，快速看到问题、决定、未响应对象和来源；
- 老师从当前会话生成讲解、通知、资源或轻活动，经确认后发送；
- 班级 Agent 被明确 `@` 后提供公开、可引用、可升级老师的回答。

### 3.4 方案一的成功条件

方案一的验证重点不是 Agent 回复量，而是：

- 老师完成同一沟通任务所需时间与轮次下降；
- 建议可直接采用或只需少量修改；
- 来源和权限错误能够在公开前被阻止；
- 学生知道回复来自老师还是 Agent；
- AI 不可用时普通聊天仍能完整工作。

## 4. 方案二：Learning Loop

### 4.1 产品定义

方案二不在方案一页面上增加 Loop 卡片，而是重新设计产品信息架构。自然聊天仍然存在，但用户的主要工作单元变为一个需要推进和收口的学习循环。

```text
Signal / Question
→ 目标与参与者
→ 教学行动或学习活动
→ 学生参与与反馈
→ Evidence
→ Outcome / Memory
```

### 4.2 独立产品表面

- **Today**：按学习价值、责任和时效组织老师的注意力；
- **Class Stage**：表达班级当前目标、正在发生的 Loop、自然交流和结果；
- **Loop Canvas**：围绕一个学习目标组织来源、参与、活动、证据和下一步；
- **Learning Memory**：由教师确认、带来源和权限的可复用学习结果。

### 4.3 可复用与不可复用

可以从方案一复用：

- ClassIn PC 已验证的视觉语言与基础交互原则；
- IM 连接、成员、文件、通知和消息可靠性框架；
- TeacherIn、班级 Agent 与学生助手的身份和可见性边界；
- `ContextSnapshot → ArtifactDraft → ProposedAction → Approval → ExecutionReceipt` 治理链；
- 真实 Adapter 与模拟 Adapter 通过同一 Interface 替换的工程原则。

不把以下内容作为方案二前提：

- 传统会话列表是首屏；
- 聊天气泡是所有学习内容的唯一容器；
- TeacherIn 必须作为右侧栏；
- AI 必须被 `@` 后才开始工作；
- 在当前 Demo 页面上持续增加卡片即可形成 Learning Loop。

### 4.4 方案二的成功条件

- 老师能清楚说出 Loop 的目标、下一步和结束条件；
- 学生知道自己当前是在自然聊天、参与活动还是提交学习证据；
- 一次互动能形成可复查的结果，而非只留下更多消息；
- 产品新增结构没有显著压低提问和参与意愿；
- Loop 的价值足以抵消页面和概念学习成本。

完整定义见[《方案二：ClassIn Learning Loop 零基产品愿景》](./IM-AI-AGENT-ZERO-BASED-PRODUCT-VISION.md)。

## 5. 方案三：从行业模式推导，而不是先命名

### 5.1 独立方案的判定门槛

一个候选只有同时改变以下至少四项，才值得作为方案三，而不是方案一的 Feature：

1. 一等产品对象；
2. 首屏与主要导航；
3. 用户每天首先完成的任务；
4. AI 的产品身份和默认主动性；
5. 人、AI 和业务对象之间的责任关系；
6. 价值闭环和核心指标。

如果一个想法只是“自动摘要”“主动提醒”“更多 Agent”“更强输入框”或“新增一个 AI Tab”，应优先归入方案一增强项。

### 5.2 当前最强组合假设：Learning Signal Network

暂定概念：**ClassIn Learning Signal Network / 学习信号与行动网络**。它组合行业研究中的 `3A Teacher Attention Radar` 与 `3C Conversation-to-Learning Case`，但两部分应先分别验证，再判断是否值得成为一个完整方案三。

它不把整个产品改造成 Loop，也不要求老师逐个进入聊天寻找问题。系统在明确授权和可解释范围内，从师生单聊、班级群聊及相关 ClassIn 事实中发现“需要人判断或行动的教学信号”，先进入教师私密的行动层，再将确认后的动作回流到正确的人、群和业务对象。

```text
自然聊天持续发生
→ AI 静默识别候选 Signal
→ 去重、聚类并形成 Case
→ 按影响、时效和责任进入 Teacher Radar
→ 老师忽略 / 合并 / 转交 / 生成干预 / 发起 Loop
→ 经授权回到单聊、群聊、课堂、作业或课程对象
→ 观察结果并关闭、升级或继续跟进
```

### 5.3 四个核心表面

| 表面 | 作用 |
|---|---|
| Teacher Radar | 跨会话展示真正需要老师判断的信号，而不是重新展示全部未读消息 |
| Case View | 聚合来源、受影响对象、已有回应、AI 判断理由、证据质量与建议动作 |
| Action Queue | 管理待批准、正在执行、失败待恢复和待复查的教学行动 |
| Conversation Return | 将老师批准的动作送回原私聊/群聊，并保留来源、身份与执行回执 |

### 5.4 与方案一、方案二的分界

- 不同于方案一：它的主入口不是某个会话，核心价值是跨会话发现和分流；
- 不同于方案二：它不要求所有事项都进入完整 Loop，很多信号可以被忽略、快速回复、转交或归档；
- 它可以把高价值 Case 升级成方案二的 Loop，也可以调用方案一完成一次轻量回复；
- 如果测试发现老师只愿在聊天内处理建议，`Learning Signal Network` 应降级为方案一的智能收件箱，而不是勉强保留为方案三。

### 5.5 三个可独立测试的方案三候选

#### 候选 A：Teacher Attention Radar

AI 在明确的数据范围内跨单聊与班级群发现重复、等待、遗漏和风险信号，带原消息证据进入老师私密雷达。老师首先处理的是“值得我判断的教学事项”，而不是全部未读消息。

独立成案的前提：它必须显著缩短老师发现与分流高价值问题的时间，并能从信号自然进入行动和复查；如果只生成摘要，则回归方案一的智能收件箱。

#### 候选 B：Delegated Class Agent

把班级 Agent 从“被 `@` 的机器人”升级为可被老师赋予目标、时限、干预预算和可用工具的临时协作成员。例如在一场讨论中负责主持、追问、总结和升级未解决问题。

独立成案的前提：教师真正愿意管理“Agent Mission”，学生能够理解其在场原因，且效果明显优于方案一中的 `@Agent` 与方案二中的 Loop 促进能力。

#### 候选 C：Conversation-to-Learning Case

把一条私聊问题或多名学生的相似消息提升为一个有 Owner、来源、目标、下一步、状态、学生响应和结束条件的 Learning Case。Case 可以选择个别答疑、群内讲解、微练习或作业订正，并在完成后保留学习证据与未解决项。

独立成案的前提：真实数据证明大量高价值沟通需要跨多条消息持续跟进，并且建立 Case 明显提高解决和收口率；如果多数问题一次回复即可结束，则它应只是方案一的按需结构化能力。

### 5.6 当前候选排序

| 候选 | 独特性 | 与真实 IM 痛点贴合度 | 教育差异化空间 | 当前建议 |
|---|---:|---:|---:|---|
| Teacher Attention Radar（3A） | 高 | 高 | 高 | 优先独立验证发现与分流 |
| Delegated Class Agent（3B） | 中 | 中 | 高 | 作为高参与度主动 Agent 实验 |
| Conversation-to-Learning Case（3C） | 高 | 高 | 高 | 优先独立验证行动与收口 |

真实聊天聚合数据已支持将 3A + 3C 组合成 `Learning Signal Network` 的最小概念探针：3A 先验证发现与分流，3C 再验证持续推进与收口；3B 在信任、权限和话题证据更充分后验证。此排序仍为 `PROPOSED`，必须经过匿名 Episode 人工复核和老师任务测试，不能直接进入生产范围。

## 6. 行业研究转化原则

行业产品的功能不应被逐项照搬。研究需要抽取可迁移的交互模式：

| 行业模式 | 对方案一的直接价值 | 对方案三的启发 |
|---|---|---|
| 私密 AI 摘要、检索与撰写 | 降低阅读和表达负担 | 跨会话注意力层需要来源与个性化权限 |
| Agent 可发现、可加入群聊、可私聊 | 完善公开与私密调用入口 | Agent 可能成为受治理协作成员 |
| 群内回答前权限检查或私密预览 | 强化教师审核和成员可见性 | 支持“先私密判断、再公开行动”的产品范式 |
| 引用来源和跳回原消息 | 提升可验证性 | Signal/Case 必须可回到证据，不成为黑箱判断 |
| 交互式操作与任务执行 | 从回答升级为完成工作 | Action Queue 与跨业务对象回写可能成为独立层 |
| 主动摘要、推荐和自动触发 | 支持低打扰主动性 | Learning Radar 需要干预预算、理由和关闭能力 |
| Agent 目录、管理员部署和权限范围 | 避免能力无序扩张 | 班级、机构和角色需要 Agent Registry 与 Policy |
| 任务日志、审批门和记忆范围 | 对齐现有 Approval/Receipt | 持续 Agent 必须有透明度、控制力和可治理记忆 |

详细一手证据见[《IM × AI Agent 行业交互模式研究》](../01-research/source-notes/industry_research_im_ai_agent_interaction_patterns_20260828.md)。

## 7. 同题三做：概念原型验证设计

### 7.1 先从真实 Episode 选题

完成首轮脱敏编码后，分别从单聊和群聊选择：

- 一个高频、高重复劳动、原流程基本有效的 Episode；
- 一个需要多人参与、活动和结果验证的 Episode；
- 一个跨多个会话出现、老师难以及时发现或持续跟进的 Episode。

不要为了适配方案而选择不同任务。每个入选 Episode 都要保留相同起因、角色、消息、业务上下文和期望结果。

### 7.2 三种原型处理同一任务

| 方案 | 原型重点 |
|---|---|
| 方案一 | 用户在原聊天中如何发现 AI、获得帮助、审核并完成沟通或行动 |
| 方案二 | 同一问题如何进入 Loop、组织参与、产生 Evidence 并形成 Outcome |
| 方案三 | 同一问题如何被跨会话发现为 Signal、进入 Radar、形成 Case 并回流行动 |

### 7.3 共同任务指标

- 首次发现有效问题所需时间；
- 从发现到采取正确行动所需步骤和时间；
- 老师理解 AI 判断及来源的成功率；
- AI 建议的采纳率、修改距离和拒绝原因；
- 学生问题得到有效回应的比例与时间；
- 学生参与率、完成率和可观察的理解变化；
- 误判、越权、公开错误和打扰率；
- 一周后用户能否找到、继续和复用结果；
- 用户主观认为“更有帮助”与“更复杂/被监控”的比例。

### 7.4 方案专属指标

| 方案 | 专属指标 |
|---|---|
| 方案一 | AI 使用是否自然发生；普通 IM 是否仍然顺畅；每次辅助节省的操作成本 |
| 方案二 | Loop 建立和收口率；Evidence 完整度；新增结构是否压低自然参与 |
| 方案三 | Signal 精准率；老师认为“值得进入 Radar”的比例；跨会话聚类和优先级是否真正减少漏看 |

## 8. 推进 Gate

### Gate 0：数据与伦理准备

- 明确授权、脱敏、保存范围和研究访问人；
- 原始消息不进入仓库；
- 不把学生敏感推断写入无治理记忆；
- 无法获得原始样本时，先由用户提供匿名 Episode 复述，不伪造统计结论。

### Gate 1：场景发现

- 单聊和群聊形成稳定的一级话题分类；
- 识别频率、负担、学生影响、未解决率和现有 workaround；
- 得到 3–5 个可进入原型的高证据 Episode。

### Gate 2：方案三资格判断

- 行业研究证明存在可迁移的新交互模式；
- 真实场景证明痛点跨越单个会话或完整 Loop；
- 候选通过“至少改变四项”的独立方案门槛；
- 若不通过，研究结果回归方案一增强，不为凑三方案制造概念。

### Gate 3：三方案概念原型

- 方案一在当前 Demo 的独立分支或配置中深化；
- 方案二新建独立概念页面树，不修改、缝补方案一页面；
- 方案三只实现最小产品探针，优先验证 Radar/Case/Return 三段；
- 三者使用同一脱敏情境和共同指标测试。

### Gate 4：工程纵向切片

只有概念测试获得明显行为证据后，才选择一条产品纵向切片进入 Feature Spec、架构变化和实现。产品方案选择不得绕过已有身份、权限、审批、回执和 Adapter Seam。
