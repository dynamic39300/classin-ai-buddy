# ClassIn TeachBuddy 阶段性汇报讲稿与演示手册

## 1. 汇报目标

这次汇报要让老板在结束时形成三个判断：

1. 当前成果不是零散功能，而是已经形成“终局双形态 + MVP 阶段落地”、统一能力骨架和清晰数据边界的教师 AI 产品系统；
2. M4.2、M4.3、M4.4 已通过产品页面验收，M4.5 正在做不改变底层业务逻辑的体验收口；
3. 下一步不是继续堆 Demo，而是选择第一条真实纵向切片，配置跨产品、IM、AI Harness、业务域和质量安全的实施团队。

建议总时长为 **30 分钟**：

- 汇报 18–20 分钟；
- 现场演示 7–8 分钟；
- 讨论和拍板 5 分钟。

## 2. 开场口径（60 秒）

> 我们今年围绕一个判断持续推进：老师真正需要的不是另一个会回答问题的聊天机器人，而是一位能理解教学现场、生成可审阅产物，并在老师确认后完成业务闭环的 AI 教学搭档。
>
> 截止目前，我们已经完成了两层产品设计。第一层是终局产品形态，它同时包含 ClassIn 站内教师工作台，以及面向非 ClassIn 客户和新教师的站外开放 AI 平台；第二层是从完整终局中选择首期范围、准备进入下一阶段实施的 MVP。今天我会先讲清楚这两层关系，再用页面和现场 Demo 说明能力如何工作，最后讨论从 Demo 走向真实实施需要怎样的团队和推进计划。

## 3. 逐段讲解重点

### Part 1：AI TeachBuddy 产品全景架构（5 分钟）

必须讲清楚：

- 产品定位分为两大部分：终局产品形态，以及阶段性 MVP；
- 终局产品形态本身包含站内、站外两种完整产品；
- 它们共享能力规则、领域接口、设计系统和内容标准；
- 它们不共享产品配置、账号、Session、任务历史、私有 Artifact、Receipt 和商业数据；
- 所有能力都沿“目标 → Context → Artifact → 审阅 → 受控执行 → Receipt/Evaluation”运行；
- 当前为固定、脱敏、可重置的高保真 Demo 与工程纵向切片，没有接真实 ClassIn API、生产模型或真实支付。

#### 终局双形态与 MVP 的关系

| 产品层级 | 产品形态 | 主要入口 | Context | 能力范围 | 主要目标 |
| --- | --- | --- | --- | --- | --- |
| 终局产品形态 | 站内 ClassIn 教师 TeachBuddy 工作台 | ClassIn 一级教师工作台 | 老师已授权的全部班级、课程、作业、消息与学情 | 完整能力 | 形成 ClassIn 内统一教师 AI 工作台 |
| 终局产品形态 | 站外独立老师 AI 教学搭档 | 独立官网、注册与登录 | 老师输入、上传资料；默认不读取 ClassIn 业务 Context | 完整独立体验 | 服务非 ClassIn 客户、新教师并形成开放获客平台 |
| 阶段性落地 | MVP 教师 TeachBuddy | 班级课程详情页 | 统一 TeachBuddy，入口优先注入当前班级 Launch Context | 首期受控能力 | 下一阶段验证 ClassIn 高价值业务现场和真实实施路径 |

建议按照以下顺序讲解：

1. **先讲终局整体**：终局不是一个站内工作台，而是同时包含站内、站外两种完整产品形态；
2. **终局站内**：利用完整 ClassIn Context，为现有客户与老师提供统一教师 AI 工作台；
3. **终局站外**：没有 ClassIn Context 也能独立闭环，为非 ClassIn 客户和新教师提供开放 AI 平台；
4. **再讲 MVP**：MVP 不是第三种终局，而是从完整终局设计中选择首期能力，准备进入下一阶段实施的产品。

三者共同复用：

- TeachBuddy 的产品理念、品牌与统一任务交互；
- Run、Context、Artifact、Action、Approval、Receipt 和 Evaluation 等能力与治理骨架；
- 教育 Skills、工具 Interface、Domain Knowledge 与 Design System；
- TeacherIn 内容格式与领域校验标准。

三者必须隔离：

- Shell、Route、Experience Profile 和能力配置；
- 账号、Session、Workspace、任务历史和私有 Artifact；
- Approval、Receipt 与评价证据；
- 独立产品的 AI 点数、会员和订单；
- MVP 功能裁剪不能影响终局产品，独立产品不能直接读取或跳转借用 ClassIn 后台。

管理层一句话口径：

> 整体产品设计分成两大部分：终局产品同时包含站内 ClassIn TeachBuddy 工作台和站外开放教师 AI 平台；MVP 则是我们从完整终局中选择首期范围、准备进入下一阶段实施的产品。三套实现共享能力标准，但产品运行和数据空间彼此独立。

第 6 页先点题“产品体验与 AI 能力设计链路”：老师看到的是从目标到回执的产品体验，系统背后运行的是从理解、生成到受控执行的 AI 能力链。随后沿“目标 → Context → Artifact → 审阅 → 受控执行 → 回执复查”讲完整流程，再用同一页下方的“有来源、可修改、写回受控、结果可追溯”解释可信治理。

第 7 页点题“TeachBuddy 层层深入的能力层级”：第一层理解业务，第二层生成内容，第三层在老师批准后执行。权限、证据、人工审批和失败恢复不是第四层，而是贯穿三层的共同要求。

一句话总结：

> 我们已经把教师 AI 最难的产品骨架先搭出来了：既能生成，也能让老师控制，还能为未来真实写回保留完整证据链。

### Part 2A：终局产品——站内 ClassIn TeachBuddy（5 分钟）

推荐重点演示两类任务能力，并用一页说明内容资源闭环：

1. 单课件生成：展示统一任务入口、Context、步骤、产物预览和确认；
2. 测验活动草稿：展示从试卷生成到课程对象草稿写回，不直接发布给学生。
3. 内容资源闭环：说明产物如何从“我的文件”进入“我的空间”和 TeacherIn，再被分享、复用或加入新的 Context。

避免逐个介绍 Skills、Tools、Files、Schedules。它们作为能力资产管理背景带过即可。

关键口径：

> 老师只需要描述任务；Agent、Skill、模型和工具的选择属于系统内部实现，不是老师要承担的认知成本。

内容资源页的讲解顺序：

1. **我的文件负责管理，不另建存储。** 它按任务投影 TeachBuddy 生成的 Artifact，展示版本、来源、复用和分享记录；底层文件仍由“我的空间”统一存储，两者共享稳定引用而不是复制文件所有权。
2. **TeacherIn 负责正式内容生命周期。** 可发布产物先经 ProposedAction、教师确认与 ExecutionReceipt 创建 TeacherIn 草稿，再由教师二次编辑、设置授权、发布和分发。
3. **AI + 人类共同生产。** TeachBuddy 负责生成、结构化和校验建议；教师负责审阅、修改、授权与正式发布。
4. **产物能够循环复用。** 可以继续分享给协作者、加入新任务 Context，或在原版本上二次编辑并派生新版本。

准确口径：

> “我的文件”是 AI 产物的管理视图，“我的空间”是文件存储载体，TeacherIn 是作品审阅、授权、发布与分发的正式业务入口。三者共享内容引用，共同形成课程生产闭环；当前 Demo 证明的是产品与证据链设计，不代表真实 TeacherIn API 已接通。

### Part 2B：终局产品——站外开放教师 AI 平台（3 分钟）

这不是站内终局牵引出来的临时获客分支，而是终局产品的第二种完整形态。不重复演示相同的课程生成能力，重点讲四项差异：

- 独立官网和个人教师账号；
- 没有 ClassIn Context 时依赖任务描述和上传资料，并明确提示能力差异；
- AI 点数、会员方案和模拟订单构成完整体验；
- 连接 ClassIn 是能力增量和获客路径，而不是独立产品偷连 ClassIn 后台。

TeacherIn 内容兼容的准确口径：

> 独立产品和 ClassIn 在运行与数据上完全隔离，但内容从生产时就遵循同一 TeacherIn 内容契约。未来连接时处理的是身份、权限和对象映射，不需要重新制作或转换内容；当前并不代表真实 TeacherIn API 已接通。

### Part 3：阶段性 MVP 与 IM（7 分钟，含 Demo）

进入这一段时先明确：MVP 是从完整终局设计中选择首期范围、准备进入下一阶段实施的产品，不属于终局的第三种形态。

必须先解释两类入口：

- “我的教学伴侣”：老师专属的一对一 TeachBuddy；
- “AI 应用”：老师授权给班级、班级成员可用的 Agent。

入口页面按角色依次讲：

1. **老师 TeachBuddy。** 先在班级详情定位“我的教学伴侣”卡片，再展示点击后打开的独立全屏 MVP 工作台；工作台优先带入当前班级 Launch Context，并提供明确的返回原班级路径。
2. **老师班级 Agent。** 在班级详情的“AI 应用”查看授权范围；在群聊输入区显式选择 `@Agent`，才触发公开回复。
3. **学生班级 Agent。** 学生没有 TeachBuddy，只能从私聊目录或班级群使用老师已授权的 Agent；私聊与公开群分别遵守不同的历史和可见范围。

已验收能力按角色概括：

- **老师侧：**核对作业提交和周计划，生成作业提醒、课前通知与单题讲解，经老师审阅后发送到群聊或学生私聊；覆盖第 1 层信息分析、第 2 层内容生成和第 3 层执行操作。
- **学生侧：**在 Agent 私聊中连续追问，或在班级群显式 `@Agent`；获得知识点说明、思考方向、分步提示和自检方法，当前聚焦第 1 层理解、分析与学习辅导。

五个 Case 总览之后，按角色讲两个完整案例，不在单页内混合多个渠道：

1. **老师视角——作业提交提醒。** 老师提出目标，TeachBuddy 读取作业事实并生成未交名单和最终群消息；老师可编辑发送范围与话术，批准后才执行并保留回执。
2. **学生视角——Agent 私聊辅导。** 学生只看到本班已授权 Agent，进入同一私聊会话连续追问；Agent 给出分步思路与自检方法，但不替学生直接完成作业答案。

若现场需要补充单题讲解，可在问答阶段演示“学生只说课程、作业和题号 → 老师生成并审阅可打开讲解 → 批准分发”的链路，不占用主讲页面。

### Part 4：实施准备（5 分钟）

明确区分已经验证和仍需建设：

| 已经验证 | 真实实施仍需建设 |
| --- | --- |
| 产品定位、入口与信息架构 | 真实账号、租户与权限 |
| 代表性业务 Case 与交互状态 | ClassIn 业务 API 与数据治理 |
| Run/Context/Artifact/审批/Receipt 契约 | 真实模型 Runtime、成本、限流与恢复 |
| Mock Adapter、领域校验和自动化测试 | 生产可观测性、灰度、安全与运维 |
| 三产品数据边界与 TeacherIn 内容标准 | 真实效果指标与业务结果评估 |

建议的团队责任域：

1. 产品与教学体验；
2. Workbench / UI；
3. IM 与 ClassIn 业务集成；
4. Agent Harness / AI Platform；
5. Skills、MCP 与 Domain Knowledge；
6. 平台、质量与安全。

每条业务场景另设一位纵向负责人，对 UI 到 Receipt 的端到端结果负责。

## 4. 现场演示 Runbook

### 演示前 10 分钟检查

- [ ] 在仓库根目录启动应用：`npm run dev -- --host 127.0.0.1`
- [ ] 浏览器打开 `http://127.0.0.1:4173/select-role`
- [ ] 重置 Demo 数据，确认老师和学生角色均可进入
- [ ] 准备两个浏览器标签：老师、学生
- [ ] 浏览器缩放为 100%，窗口建议 1440×900 以上
- [ ] 关闭无关标签、通知和自动填充弹窗
- [ ] 演示前完整走一遍 WB-06，确认状态已恢复到初始 Fixture
- [ ] HTML PPT 打开后按 `N` 可显示本页讲稿，`Esc` 关闭

### Demo A：终局课件生成（2 分钟）

路径：老师角色 → TeachBuddy → 新建任务 → 生成单个课件。

讲解动作：

1. 指出统一自然语言任务入口；
2. 选择教学 Context；
3. 启动任务并快速展示步骤时间线；
4. 打开右侧课件预览；
5. 强调“结果先审阅，确认后才进入后续任务”。

若现场时间不足：只展示已完成的课件 Artifact 页面，不重新跑生成动画。

### Demo B：测验活动草稿（2 分钟）

路径：TeachBuddy → 生成测验并创建活动草稿。

讲解动作：

1. 通过对话确认试卷结构；
2. 生成后点击查看试卷；
3. 先完成审卷，再进入活动参数；
4. 批准“创建草稿”；
5. 回班级课程详情说明仍需老师二次编辑和正式发布。

不要在演示中说“AI 已经发布测验”。准确表述是“创建了教师可见草稿”。

### Demo C：IM 单题讲解（3 分钟，主 Demo）

路径：老师角色 → 消息 → 班级群 → 学生关于第 5 题的提问 → TeachBuddy 单题讲解。

讲解动作：

1. 指出学生不会完整敲题目，只会说课程/作业/题号和卡点；
2. TeachBuddy 从当前 Context 找到题目，并生成分步讲解；
3. 老师修改最终发送话术；
4. 打开文字链接预览 H5/HTML 讲解；
5. 修改步骤或完整答案；
6. 批准后发到当前班级群；
7. 切到学生标签打开讲解内容。

备选路径：在学生 1v1 私聊中使用同一能力，说明分发目标不同、审核面相同。

### Demo D：群聊 Agent 与私聊 Agent（1 分钟，可选）

- 班级群：必须 `@物理学习助手`，答案公开、简短、不给最终答案；
- 学生私聊：搜索已授权 Agent，保留历史，显示思考/分段回复，不同会话历史互不混用。

## 5. 可能被问到的问题

### Q1：现在可以上线了吗？

建议回答：

> 产品定位、主要流程、状态和工程契约已经具备进入真实实施的条件，但当前仍是模拟数据与 Mock Adapter。上线前需要真实 ClassIn Context、权限、模型 Runtime、审计、灰度和效果指标。建议先选一条真实纵向切片，而不是整套同时生产化。

### Q2：和通用大模型/聊天工具相比，差异是什么？

建议回答：

> 差异不只是 Prompt。TeachBuddy 能获得经过授权的教学 Context，把结果生成成 ClassIn/TeacherIn 可用对象，让老师审阅和修改，并在批准后通过业务规则写回或分发，最终保留回执和评价证据。

### Q3：为什么终局同时包含站内和站外，还要单独做 MVP？

建议回答：

> 因为终局要同时覆盖两类市场：站内终局服务 ClassIn 现有客户和老师，依靠完整业务 Context；站外终局服务非 ClassIn 客户和新教师，没有 ClassIn Context 也要能独立闭环。MVP 则解决实施节奏问题：从完整终局中选择首期高价值范围，进入下一阶段实施。三套实现共享底层能力标准，但产品与数据隔离，因此可以独立裁剪和演进。

### Q4：独立产品会不会和 ClassIn 冲突？

建议回答：

> 它的定位是服务个人教师和未合作机构中的教师，并通过 ClassIn Context 增量完成转化。运行和数据独立，但内容标准与 TeacherIn 兼容，未来可以经授权受控回流，而不是形成割裂内容孤岛。

### Q5：先生产化哪一个 Case？

建议回答：

> 两个候选：作业提交提醒的业务事实清晰、风险较低，适合验证真实 Action/Receipt；单题讲解更能体现内容与教学价值，但需要题目 Context、内容存储和分发能力。建议结合用户价值、数据与 API 就绪程度选择首批真实业务切入场景。

## 6. 收尾口径

> 过去这阶段，我们验证了 ClassIn 的教师 AI 不应该停在对话框，而应该成为一个理解教学现场、生产教学内容并能受控完成业务动作的 TeachBuddy。
>
> 现在方向、产品结构和主要业务样板都已经清楚。下一步需要确认的是首条真实切片、跨团队 Owner 和分阶段投入方式，把已经验证的产品骨架换上真实 Context、Runtime 和业务 Adapter。
