# IM 会话 Topic 校准规则 v1.1（草案）

> 用途：吸收阶段 A 前 50 个窗口的两轮人工反馈，为阶段 B 的顺序样本提供可执行规则。状态为 `CANDIDATE_FROZEN_FOR_STAGE_B_20260901`；它不覆盖原方法、taxonomy v1 或既有自动结果。阶段 B 如需修改，必须产生后续版本并保留差异。

## 1. 五个相互独立的裁决问题

对每个自动 Topic 依次判断，禁止用一个“认同／有问题”替代全部维度：

1. **成立性**：完整上下文是否确实存在这个独立话题；
2. **边界**：应保持一个事项，还是与其他 Topic 合并／拆分；
3. **证据**：哪些消息真正支撑该 Topic；
4. **准入**：属于 standard、special_business、short_candidate，还是待研究的短业务动作；
5. **分类**：内容主轴应落到哪条 L1 / L2 / L3 路径。

分类修正不自动改变准入资格；准入修正也不自动证明名称、证据或路径正确。

## 2. Topic 命名

- 名称描述当前窗口中实际发生的沟通事项，不写产品机会、AI 价值判断或角色关系标签；
- 优先使用“对象 + 动作／事项”，避免只抄一个名词；
- 描述只补充证据可见的参与动作、目标和限制，不推断窗口之外的结果；
- 一段聊天同时出现多个名词时，以持续推进的主事项命名，而不是把所有名词串成标题；
- 工具、入口或链接只是实现手段时，名称应表达其实际用途。

## 3. 分类主轴

分类前按顺序回答：

1. 参与者实际在做什么？
2. 讨论的核心对象是什么？
3. 这是学生在学习内容、教师在准备教学、课程服务在协同，还是日常／社交交流？
4. 文中出现的软件、账号、课程、论文、教材等名词，是主对象还是背景工具？

选择主路径时，以主要沟通对象、动作和实际用途为准，不能用单个关键词命中。角色关系进入 `scene_label`，不进入 Topic 目录。

### 3.1 常见判定边界

| 容易混淆的信号 | 先判断 | 规则 |
|---|---|---|
| 账号、软件、链接、在线入口 | 是否正在解决数字工具本身的问题 | 工具只是聊天／见面／授课的媒介时，按实际活动分类；故障、登录和权限本身才进入数字技术 |
| 课程、补课、上课时间 | 是否在真实协调当前课程服务 | 同伴随口谈自己的安排不等于课程运营；明确改期、预约、出勤才是课程服务 |
| 教材、资料、课件 | 谁在选、制作、获取或使用 | 学生学习具体内容、教师教学准备、机构课程配置分开判断 |
| 论文、投稿、研究 | 是学习辅导还是专业研究活动 | 教师—学生辅导不能只因“论文”落入研究经济；需要明确的论文／学术写作边界 |
| 编程、软件、技术名词 | 是学习代码，还是使用某软件 | 代码、算法和编程任务进入编程学习；任意软件的登录、卡顿、更新仍属于数字工具问题 |
| 角色称谓、家庭称呼 | 是持续虚构创作，还是朋友玩笑 | 亲昵称呼和短暂玩笑进入社交；有持续设定、情节或共同创作才进入角色文化 |

阶段 A 最终复核补充两条“上下文优先”规则：

- 软件安装、调试、实现或故障如果本身是编程课程正在教授、练习或完成的对象，应按编程与计算学习语境判断；只有软件作为授课／沟通工具而参与者处理登录、连接、权限或卡顿时，才按数字平台与技术判断。
- 论文写作、修改和投稿如果由导师／教师作为学生学习任务持续辅导，不应仅凭“论文”“期刊”落入专业研究活动；独立研究项目和职业发表仍属于学术研究。taxonomy v1 暂无稳定承载“论文辅导学习任务”的叶节点时，应标记 taxonomy conflict，不强塞到宽泛节点。

“角色扮演与虚构互动”的正例应出现明确共同扮演前提、角色分工或持续情节，例如“我扮演什么、你扮演什么”。只有妈妈、孩子、保姆等称谓，但上下文体现昵称、亲切感、特殊指代或风趣调侃时，应归入轻松闲聊与玩笑。

兜底节点只在正文／对象确实无法辨认或 taxonomy 尚无可容纳节点时使用，不能因为“不属于 ClassIn 产品”就投入兜底。

## 4. 合并、拆分与跨域

- 同一对象、同一目标、连续推进的问答或状态变化合并为一个 Topic；
- 对象、目标或后续行动独立，且各自有足够证据时拆分；
- 人工选择“需拆分”只有同时给出拆分后的 Topic 名称／描述及各自证据边界时才可自动执行；只有拆分方向时保留原 Topic 的可执行修正，并把拆分登记为显式例外；
- 一条消息同时支撑两个独立事项时允许多重证据映射；
- 跨域事项仍选择一个主路径，辅助内容进入 secondary tags；
- 如果现有目录轴无法稳定选择主路径，先标记 taxonomy conflict，不强行选择“看起来更重要”的节点。

## 5. 准入资格

### 5.1 既有分轨

- `standard`：有效证据达到窗口消息数的 5%；
- `special_business`：满足当前方法中对群聊单向公告、提醒、排课或明确行动要求的严格例外；
- `short_candidate`：不足 5%，也未满足已冻结特殊例外。

所有分轨都可以拥有候选分类路径；只有 formal 资格进入主统计。

### 5.2 短业务动作候选

阶段 A 暴露出 1v1 调课、简短课程动作、学习反馈请求等不足 5% 但可能具有独立业务意义的事项。阶段 B 先用 `short_business_action_candidate` 做研究标签，不直接扩大正式统计口径。

候选必须同时满足：

- 有明确业务对象；
- 有清楚的请求、决定、状态变化、结果反馈或待执行动作；
- 可由完整原文独立还原；
- 不是随口提及、情绪表达或产品团队主观认为“重要”；
- 记录是单向通知、双向交易还是里程碑反馈。

经过 B 样本验证后，再决定将其并入 `special_business`、新建正式资格，或继续只作候选。禁止以“未来可能做 AI 功能”为准入理由。

如果 v4 反馈先导入新版审阅台再导出为 v5，而“短候选应成为正式主题”的意图仍只存在于备注，裁决器必须继续 fail-safe：保留源 `short_candidate`，登记 `qualification_change_requested_only_in_note`，不得因 schema 升级而静默丢失人工意图，也不得自动改成 `standard`。

## 6. 目录变更候选

taxonomy v1 暂不原位修改。以下只进入 v1.1 变更候选：

- 将教材相关节点用“选用／适配”与“制作／获取／传送／处理”的动作边界重新定义，先不直接合并；
- 为迟到、扣罚等跨越出勤、教师事务和费用结算的事项增加决策树；
- 评估新增“论文与学术写作／投稿”节点，区分学习辅导与专业研究；
- 明确数字技术节点覆盖一般软件，编程学习节点只覆盖代码、算法及学习任务；
- 检查兜底节点是否被用来逃避已有节点的纳入规则。

目录发生增删改名或语义边界变化时必须产生新版本和旧—新映射，不能覆盖 v1。

## 7. 人工审阅完成条件

一个窗口只有同时满足以下条件才算本轮人工审阅完成：

- 窗口中每个可见 Topic 都有 decision；
- 会话级完整性已判断；
- 所有“有问题”至少有问题类型或结构化修正；
- 分类错误有目标路径或明确标记为待决；
- 资格错误有目标资格；
- 场景标签已填写或明确选择“无法判断”；
- 待决项可被单独导出，不会混入“认同”。

## 8. 阶段 B 抽查策略

阶段 B 的顺序 30 个窗口保持自然样本，不因内容有趣程度替换。分析时应用本草案并分别报告：

- 卡片成立性与文字；
- formal Topic 的 L1 / L2 / L3 路径；
- short candidate 的候选路径与准入争议；
- 会话完整性；
- 窗口级场景标签。

同时增加一个不进入自然比例的规则触发审计队列：表层工具词、跨轴节点、短业务动作、兜底节点和模型高置信结果。阶段 A 表明高置信并不能替代抽审。
