## 一、执行摘要

用户对现状的两类概括方向正确：ClassIn 当前同时存在“以独立 Agent 进入班级或会话”和“AI 作为工具嵌入教师业务流程”两类用户可见形态。但从 AI Native 产品架构看，只用这两个入口形态描述现状还不够；截图已经暴露出至少四个需要分层理解的系统：

1. **业务上下文层**：班级、课程、教学方案、作业、学习活动、消息与学生权限；
2. **交互入口层**：Agent 对话、班级侧栏 AI 应用、业务页面内 AI 按钮、单聊/群聊输入框；
3. **能力供给层**：AgentIn 的发现、收藏、创建、导入、分类、可见范围与适用场景；
4. **运行与治理层**：模型、提示词、变量、输入输出方式、班级知识、Flowin 知识、引用、历史、评价和权限控制。

因此，现阶段不能把 AgentIn 简单理解为“需要被 WorkBuddy 替换的 Agent 商店”。从截图可验证的产品职责看，它已同时承担能力注册、创作者配置、跨产品分发、知识绑定和运行入口。更稳妥的终局关系是：**WorkBuddy 成为教师需求侧的默认主 Agent 与编排入口；AgentIn 保留为能力供给、创建、治理与分发层；具体能力在任务上下文中被 WorkBuddy 调用，而不是要求普通教师先理解并挑选内部 Agent。**

这一结论与 D-001 的“统一教师 WorkBuddy 工作台”方向一致，但不等于立即删除 AgentIn，也不意味着学生侧长期陪伴型 Agent、机构策划的垂直 Agent 或创作者后台没有独立存在价值。

## 四、已沉淀的 AI 资产：可见证据与复用边界

### 4.1 可确认已经形成的产品资产

- Agent 注册、商店发现、分类、收藏、历史与公开范围；
- 官方模板与自定义 Agent Builder；
- Coze、Flowin、FastGPT、元器等外部 Agent 导入入口；
- 模型、Prompt、变量、输入方式、输出方式和推理参数配置；
- ClassIn 班级知识与 Flowin 知识的挂接；
- 多模态知识文件入口与带引用的知识问答体验；
- 班级级 Agent 安装、教师/学生角色与学生可用开关；
- 教学方案、作业出题/批阅、语文/英语 AI 活动、AI 学情等垂直业务入口；
- 重新生成、复制、赞踩和建议追问等基础运行反馈。

### 4.2 不能由截图确认是“可复用 AI 中台资产”的部分

以上是**可见的产品能力和配置表面**，不自动等于 WorkBuddy 可以直接复用的中台资产。以下仍需代码、接口、组织归属和运行数据证明：

- 是否存在稳定统一的 `Capability Manifest`、调用协议、版本和健康状态；
- 各 Agent、AI 活动、AI 学情和业务 Copilot 是否共用运行时，还是彼此独立实现；
- ClassIn 业务对象、权限与知识引用是否有统一 Context 接口；
- WorkBuddy 是否可以无 UI 跳转地调用现有 Agent / Skill，并获得结构化结果；
- 生成结果是否具备稳定 Artifact ID、版本、来源、审核和写回回执；
- 模型成本、延迟、成功率、安全事件、教师修改率和真实任务完成率是否统一观测；
- 外部平台的 Token / API Key 是否采用安全托管、最小权限、轮换、脱敏与审计。

## 五、当前设计的优势

1. **AI 已经进入真实教学对象，而非停留在独立聊天框。** 班级、作业、教学方案和学习活动都具备上下文入口。
2. **作业预批阅体现了正确的教师控制。** “AI 先产出草稿、教师再确认”比直接替教师发布或评分更符合高风险教育场景。
3. **班级知识与引用形成了可解释基础。** 关联班级知识并显示参考资料，使回答具备追溯入口。
4. **模板体系编码了教师工作分类。** 学生自学、发作业、批作业、出题、授课分析、课上互动、备课/写材料等分类为后续能力编排提供了可利用的领域标签。
5. **能力供给并非封闭系统。** 自建与多平台导入说明 ClassIn 已探索能力生态和适配层，而不只是单一官方模型体验。
6. **学生侧已有真实分发闭环。** 教师加入班级的 Agent 会成为学生可见的班级 AI 应用，说明“配置—授权—学生使用”链路在产品表面已形成。

## 六、批判性评估与主要分歧

### 6.1 “两种 AI 形态”的描述正确但维度混杂

“独立 Agent”和“嵌入工作流的 AI 工具”是交互形态，不是完整业务架构。AgentIn 内部同时包含供给、创建、知识、运行和分发；AI 学情又依赖结构化业务数据，不能只按“聊天 Agent”理解。后续摸底应按四层地图展开，否则很容易把入口整合误当作能力整合。

### 6.2 不认同“有 WorkBuddy 后不再需要独立 Agent”的绝对表述

更准确的说法应是：**教师默认不需要选择内部 Agent，WorkBuddy 负责理解任务并调用能力；但独立 Agent 仍可作为供给资产、学生侧持续角色、机构策划应用、创作者产品或专家直达入口存在。**

WorkBuddy 解决的是需求侧的认知负担和跨任务编排，不天然取代供给侧注册、治理、测试和分发。

### 6.3 AI 学情不应和李白、杜甫等人格 Agent 视为同类产品

AI 学情消费课堂、作业和学生结果等结构化事实，并生成报告和干预建议；它更接近垂直领域应用或分析 Agent。其权限、证据、评价、错误成本和写回动作均高于通用对话 Agent。若继续在同一列表和同一状态模型中表达，会弱化数据来源和教师决策风险。

### 6.4 当前系统把能力选择和组织成本推给教师

教师需要进入商店、理解 Agent 名称、收藏、逐班添加、配置学生是否可用，并在多个 Agent 之间切换。左侧栏会随收藏和班级安装增长。这个模式适合早期能力探索，却不适合高频教师任务；WorkBuddy 的价值应是让教师表达目标并看到被调用的能力与依据，而不是先维护一套 Agent 菜单。

### 6.5 入口与权限存在重叠语义

截图同时出现“允许学生使用 AI 写作/绘画”和“允许学生使用 AI 应用”等班级开关。二者是总开关、能力级开关、产品级开关还是历史并存入口，截图无法判断。若教师不能预测开关结果，会直接造成学生侧可见性与合规风险。

### 6.6 当前对话以 Agent 为中心，尚未以任务和 Artifact 为中心

可见历史、收藏和入口都围绕 Agent；截图没有呈现一次教师任务如何跨多个能力持续、如何形成可复用 Artifact、如何版本化、如何进入作业/班群/课程、如何保留教师确认和执行回执。这正是 WorkBuddy 需要补的系统层，而不是再增加一个更大的聊天窗口。

### 6.7 Builder 的专业配置面与普通教师任务面需要彻底分层

模型、随机性、Token 长度、外部 App ID / API Key 等适合能力创作者或管理员，不宜成为普通教师完成教学任务的前置知识。公开查看完整提示词也可能造成提示词资产泄露、注入攻击和规则绕过；需要明确发布后的可见范围和安全治理，不能只按“透明”视为体验优点。

### 6.8 IM 是高价值上下文入口，但不应直接等同于 Agent 执行面

单聊和群聊天然包含人、班级、历史消息和待发送对象，是触发 WorkBuddy 的强入口。但群聊中的 AI 行为涉及谁可见上下文、谁授权调用、AI 回复代表谁、是否自动发消息、生成内容是否先私下预览等问题。当前红框批注只提出入口位置，尚未形成可执行的交互和权限链路。

## 七、建议用于下一轮共识讨论的系统关系

以下仅是研究后的架构假设，不升级为锁定决策：

```text
ClassIn 业务上下文（班级 / 课程 / 作业 / IM）
                    ↓ 触发与回流
          WorkBuddy（教师需求侧主 Agent）
                    ↓ 选择、组合、审批
 AgentIn / AI 中台（能力注册、知识、模型、工具、治理）
                    ↓ 结构化结果
       Artifact → 教师确认 → ClassIn 业务写回
```

- **ClassIn** 继续拥有教师、班级、课程、作业、消息和正式状态；
- **WorkBuddy** 负责目标澄清、上下文快照、能力编排、Artifact、教师审批和执行回执；
- **AgentIn / AI 中台** 负责能力供给、版本、模型/知识配置、评测、权限与分发；
- **业务页面与 IM** 是上下文入口和结果回流渠道，不各自复制一套主 Agent；
- **学生侧 Agent** 需要与教师 WorkBuddy 分开定义生命周期、权限和评价标准。

## 八、进入 MVP 规划前必须补齐的证据

### P0：决定 MVP 边界前必须明确

1. 当前 AI 能力的真实使用漏斗：曝光、添加、首轮对话、任务完成、复用和放弃；
2. 教师与学生的使用占比，以及不同 Agent / AI 工具的头部场景；
3. 每项能力的产品、算法、数据、API 和运行时所有者；
4. WorkBuddy 能否调用现有 Agent / AI 工具的稳定接口，而不是只能跳转页面；
5. 班级知识、作业、学情和 IM 上下文的权限边界、审计与最小暴露规则；
6. AI 输出如何生成稳定 Artifact、版本、来源、教师修改记录和业务写回回执；
7. 班级 AI 两组开关的层级和学生侧最终可见规则；
8. AI 学情的数据来源、证据粒度、误差处理与教师采取行动的闭环。

### P1：影响方案质量但可在第一轮后补充

1. AgentIn 的创建者画像：普通教师、机构管理员、教研人员或内部运营各占多少；
2. 公开 Agent 的发布、审核、下架、版本升级和质量评价机制；
3. 外部 Agent 导入的凭据托管、安全审计和失效恢复；
4. 班级知识索引更新、引用准确率、删除与成员变更传播；
5. 直接进入专家 Agent 与由 WorkBuddy 编排的效率差异；
6. 单聊 / 群聊内触发 AI 时的预览、发送身份、群成员可见性和撤销规则。

## 九、对下一阶段的直接影响

现阶段最重要的不是立刻确定 WorkBuddy 放在哪一个按钮，而是先形成一份“能力资产 × 业务上下文 × 用户角色 × 权限 × 产物去向”的现状矩阵。完成矩阵后再选择 MVP 场景，才能保证 MVP 是终局架构的可演进子集，而不是把一个新的聊天入口叠加到现有碎片之上。

本轮不建议锁定 MVP 功能优先级，也不建议依据截图开始改动现有 ClassIn 页面。下一轮讨论应先对齐三件事：

1. AgentIn 的终局职责是否接受“供给与治理层”定位；
2. 教师 WorkBuddy 与学生侧 Agent 是否明确分轨；
3. 老板业务输入要求优先改造的教师任务究竟是哪一条，并用真实使用与接口资产证据验证。

## 十一、后续澄清输入：IM 首个试点与双 Agent 机制

- 澄清来源：[落地设计方案的决策澄清](https://app.notion.com/p/3c4a5c3b026b80c7b631fc3456033688?pvs=204)
- 记录日期：2026-08-22
- 记录性质：用户方案输入与待讨论边界；尚未升级为锁定决策或 MVP Spec

### 已澄清的方案输入

1. **首个局部试点是 IM。** 课程详情页当前的班级 Agent 配置入口先保留，继续承担教师将 Agent 添加并授权到班级的链路。
2. **课程详情与 IM 是同一能力的不同交互界面。** 已被教师配置到班级且对学生授权的垂直 Agent，可以从课程详情、与 Agent 单聊或班级群聊中的 `@Agent` 进入。
3. **WorkBuddy 只面向教师。** 学生不可见、不可调用；教师在私密窗口中与 WorkBuddy 交流，可以选择聊天或班级上下文，生成内容、文件、材料、视频或拟执行任务。
4. **WorkBuddy 的外部动作必须经过教师确认。** 生成结果先私下预览，教师可编辑、选择接收对象并确认后，再发送到一对一聊天或班级群，或执行相应业务任务。
5. **普通班级 Agent 被设想为群内公开的虚拟成员。** 已获班级授权的老师和学生均可 `@`，Agent 可以直接在群内公开回复；学生搜索 Agent 时只应看到其当前有权使用的范围。
6. **IM 首版希望同时提供两类能力。** 一类是公开的 `@特定 Agent`，另一类是仅教师可见、以私密小窗运行的 WorkBuddy；二者虽可能都由 `@` 或聊天入口触发，但使用机制不同。

### 仍需补齐的逻辑边界

#### 1. “已授权使用 Agent”不能等同于获得全部聊天与数据权限

班级授权至少包含多种不同权利：在班级中可见、允许单聊、允许群聊提及、允许读取提及消息、允许读取更长聊天上下文、允许读取班级知识、允许读取结构化业务数据、允许调用工具、允许公开回复。若继续使用一个总开关，教师无法预测 Agent 在不同界面的实际行为。

因此，需要进一步确认现有“添加到班级 / 允许学生使用”究竟只解决可见与使用资格，还是已经包含群聊读取和公开回复授权。截图本身不能证明后者。

#### 2. 学生与 Agent 单聊和群聊并非完全等价

底层能力可以相同，但群聊增加了共同受众、消息永久性、他人信息暴露、通知打扰、刷屏、并发提及、群体评价与老师管理责任。同一回答在单聊中只影响提问学生，在群聊中会成为全班可见内容。

“公开 Agent 可以直接回复”可以作为目标体验，但仍需定义：只读取被 `@` 的单条消息还是读取前文、是否显示引用范围、是否限制连续回复、老师能否停止生成/撤回/禁言、错误回答如何纠正、同一时间多人提及时如何排队。

#### 3. “教师权限最大”仍不应被解释为默认读取全部数据

教师拥有班级管理职责，但不必然意味着每一次 WorkBuddy Run 都应读取全部私聊、学生档案、课堂录制和历史材料。更稳妥的模型是教师拥有较大的**可授权范围**，每次运行仍按任务选择最小必要上下文，并显示来源、敏感数据范围和将要执行的动作。

还需确认机构管理员规则、未成年人隐私、学生与家长可见性，以及教师是否有权把一对一聊天内容带入班级群生成任务。

#### 4. 在群聊中使用 `@WorkBuddy`，但不让群成员看见，需要明确交互语义

如果教师直接在公共输入框输入 `@WorkBuddy`，用户容易理解为即将发送到群内，也存在误发送或上下文泄漏风险。需要明确它是：

- 输入框中的本地私密命令，内容不会进入群消息；
- 从群聊打开的教师私密侧窗，并显式选择需要引用的消息；
- 或先形成只有教师可见的私密草稿，再由教师确认转为标准群消息。

无论采用哪一种，都应持续显示“仅你与 WorkBuddy 可见”，并让教师清楚当前内容尚未发送。

#### 5. “同一底层 Agent，多元交互界面”需要运行态隔离

课程详情、Agent 单聊和班级群聊可以复用同一个能力定义，但不能默认复用同一份会话历史、记忆和上下文。否则可能把学生单聊内容带入群聊，或把一个班级知识带到另一个班级。

后续需要明确：会话按用户、班级和渠道如何隔离；角色与渠道如何改变 Prompt、Skill、可读数据和输出策略；跨界面继续对话时是显式携带上下文还是重新开始。

#### 6. 把 Agent 作为“班级群成员”需要补齐 AI 身份与治理

产品可以把 Agent 设计成虚拟角色，但不能在责任与可信度上完全等同真人。至少需要持续标识 AI 身份、能力范围和回答依据，并提供教师停用、移除、限制频率、查看异常和处理举报的入口。

还需明确 Agent 是否出现在群成员列表、是否计算成员数量、是否能主动发言、谁对其输出负责，以及 Agent 下架或版本更新后班级里的实例如何处理。

#### 7. IM 首版同时提供两套机制，仍需收窄首条验收链路

`@特定 Agent → 群内直接回复` 与 `教师唤起 WorkBuddy → 私密预览 → 确认发送/执行` 是两套不同的权限、状态和异常流程。即使首版都保留产品位置，工程与验收仍宜各选一条代表性纵向链路，避免用两个入口的静态展示代替闭环验证。

可用于后续讨论的最小代表链路是：

- 公共 Agent：学生或教师 `@` 一个已授权的学科 Agent，Agent 基于明确可见的消息与班级知识生成文本回答，并公开标识 AI 与引用；首条链路不执行班级管理动作。
- 教师 WorkBuddy：教师从班级群打开私密 WorkBuddy，选择若干消息与一项班级业务数据，生成待发送通知；教师编辑、核对接收范围并确认后发送，系统保留执行回执。

以上链路只是用于暴露状态与权限问题的研究建议，不表示已确定 MVP 范围。
