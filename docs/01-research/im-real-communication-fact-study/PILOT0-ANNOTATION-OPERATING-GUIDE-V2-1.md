# ClassIn IM Pilot 0 可溯源开放编码标注操作指南

> **版本通知（2026-08-30）**：本指南未区分窗口内单方可见样本与双方可见互动样本，且“出现回应”字段容易被理解为“后来是否获得回答”。当前方法审阅请使用 [v2.3.2 一体化审阅操作指南](./PILOT0-ANNOTATION-OPERATING-GUIDE-V2-3-2.md)；本文件仅保留审计轨迹。

## 1. 这次标注到底要做什么

这不是让标注者把消息塞进预先设计好的“教学主题”，也不是判断应该开发什么 AI 功能。第一轮只做三件事：

1. 用中性语言说明消息直接表达了什么；
2. 用自己的短语记录这段沟通正在发生什么；
3. 判断一件事情有没有明确发起、回应、推进和结果证据。

主题 Codebook 要等 A/B 独立标完后，依据真实开放码归并形成。标注阶段不要追求“标准答案”，而要追求每个判断都有可见证据。

## 2. A、B 两个文件怎么用

- 标注员 A 只使用 A 文件；标注员 B 只使用 B 文件；
- 两人标注前、标注中都不查看对方答案；
- 两个文件中的原表字段、消息顺序和样本完全相同；
- A/B 差异是研究证据，不要提前讨论后改成一致；
- 一个人不能同时填写 A 和 B，否则无法衡量独立判断的一致性。

文件中的“真实值”只表示原始 Excel 已有字段值。可以用 `source_excel_row` 回原表定位，但不要外部搜索昵称、账号或真人身份。

## 3. 先分清哪些表要填

| 工作表 | 用途 | 是否填写 |
| --- | --- | --- |
| `00_使用与溯源说明` | 确认净室规则、理解回查方式 | 只填写“已确认”（10:00，已确认） |
| `00A_填写示例` | 查看虚构的规范填写案例和错误示范 | 只读，建议先看（10:20，正在看） |
| `01_样本与会话映射` | 查看 `sample_id` 与原表 `clusterid` | 只读（） |
| `02_原表字段索引` | 用原表行号、ID、昵称和原始字段精确回查 | 只读 |
| `03_逐条开放编码` | 对黄色核心消息逐条标注 | **主要填写** |
| `04_事项汇总` | 把同一件事的连续消息合并为一个事项 | **每个样本完成后填写** |
| `05_样本总结` | 总结整个样本的事实、主题和上下文缺口 | **每个样本填写一行** |
| `06_字段问题` | 登记影响判断的数据或字段疑问 | 有疑问才填 |
| `07_样本保全` | 检查样本没有丢失或替换 | 只读 |

## 4. 推荐工作顺序

一次只处理一个 `sample_id`：

1. 在 `03_逐条开放编码` 找到该样本；
2. 先读灰色上下文行，不填写；
3. 顺序读完20条黄色核心行，先理解整体对话；
4. 回到第一条黄色行，逐条填写；
5. 给围绕同一事项的消息分配同一个 `local_event_id`；
6. 在 `04_事项汇总` 汇总这个样本的事项；
7. 在 `05_样本总结` 完成该样本总结；
8. 再处理下一个样本。

不要读一条就立刻猜主题。先完整阅读该样本，可以明显减少把“收到”“在吗”“今天好难”等短消息误标成独立任务。

### 首次填写建议

不要一上来连续标完24个样本。建议两位标注者各自按以下节奏执行：

1. 先只阅读 `00A_填写示例`，理解字段，不在正式样本里练习；
2. 独立完成文件中最前面的2个 `sample_id`，期间不交流答案；
3. 只做结构检查：有没有误填灰色行、漏填必填项、把产品建议写进开放码、把“收到”写成完成；
4. 若字段定义仍有歧义，先登记到 `06_字段问题`，再统一修订规则；
5. 规则确认后继续完成余下样本，已经填写的原始判断保留，不因查看另一人的答案而改写。

这一步是填写流程试运行，不是提前统一主题答案。

## 5. `03_逐条开放编码` 最低填写标准

### 5.1 只标黄色核心行

灰色 `上下文-只读` 行只帮助理解，不填任何标签。黄色 `核心-需标注` 行需要填写。

### 5.2 核心行必填字段

| 字段 | 怎么填 |
| --- | --- |
| `可理解程度` | 清楚 / 部分清楚 / 无法理解 |
| `事实性概括` | 一句中性短句，只写直接可见内容 |
| `开放码1` | 最能概括当前沟通行为或对象的自由短语 |
| `明确提问` | 是否明确向对方索取事实、解释或答案 |
| `明确行动请求` | 是否明确要求对方完成一个行动 |
| `明确时间要求` | 是否直接出现时间、日期、时限或截止要求 |
| `提交/分享物` | 当前消息是否实际提交、发送或明确声明已分享内容 |
| `出现回应` | 当前消息是否在回应前文可见事项 |
| `结果证据` | 完成 / 未完成或受阻 / 仅有进展 / 未看到 / 无法判断 |
| `上下文依赖` | 低 / 中 / 高 / 无法判断 |
| `推断警报` | 有推断就写明；没有填“无” |
| `local_event_id` | E1–E5 / NONE / UNKNOWN |

### 5.3 选填字段

- `开放码2`、`开放码3`：一条消息确实包含第二、第三个可区分行为或对象时才填；
- `标注备注`：记录难点、另一种合理解释或仲裁时需要关注的点；
- 不要为了填满表格而制造多个开放码。

## 6. 每个字段的准确判断方式

### 6.1 可理解程度

- `清楚`：不猜测即可说明消息做了什么；
- `部分清楚`：大体能理解，但对象、指代或目的缺失；
- `无法理解`：纯符号、载荷缺失、严重截断或必须依赖不可见内容。

“内容很短”不等于无法理解。例如“收到”行为本身清楚，只是它是否代表事情完成可能无法判断。

### 6.2 事实性概括

推荐结构：`发送者 + 直接做了什么 + 明确对象/结果`。

- 合格：“发送者询问第二天的开始时间。”
- 合格：“发送者确认已进入某个活动。”
- 合格：“发送者表达题目难，没有提出请求。”
- 不合格：“学生需要 AI 帮忙解题。”——身份、需求和产品解法都不是直接事实。
- 不合格：“老师在催作业。”——如果原表角色或上下文不能证明老师身份，就不能这样写。

事实性概括不是复制原文，也不是主题名；通常15–40字足够。

### 6.3 开放码

开放码是简短、可复用的事实短语，建议写成“动作 + 对象”：

- `询问开始时间`
- `告知时间安排`
- `请求提前进入`
- `确认已进入`
- `表达题目困难`
- `请求提交图片`
- `分享文件`
- `确认收到`

禁止写：

- `需要AI提醒`
- `应该增加作业助手`
- `高价值教学需求`
- `用户体验不好`

这些是产品解释，不是开放码。

### 6.4 明确提问与明确行动请求

两者可以同时为“是”，但判断对象不同：

- “明天几点开始？”：明确提问=`是`；行动请求=`否`；
- “请把文件发给我”：明确提问=`否`；行动请求=`是`；
- “你能告诉我几点开始并把链接发来吗？”：两者都=`是`；
- “在吗？”：通常是注意力呼叫，不是索取具体信息；明确提问=`否`，行动请求=`否`；
- 反问或感叹有问号，也不自动算明确提问。

### 6.5 明确时间要求

只有文本或可见上下文直接出现时间信息才选“是”：

- “今晚8点前”“明天下午”“下课后提交”均为“是”；
- “尽快”“有空的时候”可记录在事实概括，但若没有可执行时间边界，通常选“否”；
- 消息自身的发送时间不等于内容中的时间要求。

### 6.6 提交/分享物

它描述 **当前消息是否实际提交或分享**，不是是否请求别人提交：

- “这是第3页作业”并附内容：`是`；
- “文件已经发群里了”：`是`；
- “请把第3页拍照发群里”：`否`，但行动请求=`是`；
- 只看到“[文件]”但载荷不可见：可选`是`，同时在推断警报说明附件内容不可见。

### 6.7 出现回应

当前消息是否针对前文可见内容作出回应：

- 回答问题、确认收到、补充信息、拒绝、纠正都算回应；
- `replymsgid` 非零是重要线索，但不能自动证明回答了什么或解决了问题；
- 核心片段第一条若只靠窗口外内容才能知道是否回应，选“无法判断”。

### 6.8 结果证据

- `完成`：目标结果明确出现，例如“已经提交”“已进入”“改好了”；
- `未完成或受阻`：明确出现失败、拒绝、权限问题或仍未完成；
- `仅有进展`：正在处理或提交了中间材料，但最终结果未出现；
- `未看到`：当前片段没有结果证据；
- `无法判断`：内容或上下文不足，连结果类型都无法识别。

“收到”默认只是回应，不等于事情完成。只有原事项的预期结果本身就是“确认收到”时，才可以视为完成。

### 6.9 上下文依赖

- `低`：仅看当前消息即可稳定判断；
- `中`：需要前后几条可见消息；
- `高`：关键对象、目的或结果依赖窗口外/缺失内容；
- `无法判断`：消息本身不可理解。

### 6.10 推断警报

这个字段不是让标注者写结论，而是提醒自己“哪里可能猜过头”。

- 没有推断：填`无`；
- 有推断：“可能在回应窗口外问题”“昵称像老师，但系统角色未知”“附件内容不可见”；
- 如果某个判断只能靠推断成立，应优先改成未知，而不是保留高风险标签。

### 6.11 local_event_id

围绕同一对象、同一期望结果并连续推进的消息使用同一个事件编号：

- `E1`：第一个明确事项；
- `E2`：第二个独立事项；
- `NONE`：问候、纯表达、无明确事项；
- `UNKNOWN`：可能有关联事项，但上下文不足无法切分。

不要因为每条消息来自不同发送者就拆事件，也不要因为都提到“课程”就把不相关事项合并。

## 7. 一组完整的虚构示例

下面只是填写方法示范，不属于研究样本，也不会成为主题标准答案。

### 示例消息 1

原文：“明天几点开始？”

- 可理解程度：清楚
- 事实性概括：发送者询问第二天的开始时间
- 开放码1：询问开始时间
- 明确提问：是
- 明确行动请求：否
- 明确时间要求：是
- 提交/分享物：否
- 出现回应：否
- 结果证据：未看到
- 上下文依赖：低
- 推断警报：无
- local_event_id：E1

### 示例消息 2

原文：“明天19:00开始，请提前10分钟进入。”

- 事实性概括：发送者告知开始时间并请求对方提前进入
- 开放码1：告知开始时间
- 开放码2：请求提前进入
- 明确提问：否
- 明确行动请求：是
- 明确时间要求：是
- 提交/分享物：否
- 出现回应：是
- 结果证据：未看到
- 上下文依赖：低
- local_event_id：E1

### 示例消息 3

原文：“收到，我已经进入了。”

- 事实性概括：发送者确认收到信息并表示已经进入
- 开放码1：确认已进入
- 明确提问：否
- 明确行动请求：否
- 出现回应：是
- 结果证据：完成
- 上下文依赖：中
- local_event_id：E1

### 示例消息 4

原文：“今天这道题太难了。”

- 事实性概括：发送者表达题目困难，没有提出请求
- 开放码1：表达题目困难
- 明确提问：否
- 明确行动请求：否
- 结果证据：未看到
- 上下文依赖：低
- local_event_id：NONE

禁止把它自动写成“知识答疑需求”“学习任务”或“需要 AI 解题”。若后续出现明确求助，再将后续消息和它放进同一事件或新的事件。

### 示例消息 5

原文：“麻烦今晚8点前把第3页拍照发群里。”

- 事实性概括：发送者要求对方在今晚8点前提交第3页图片
- 开放码1：请求提交图片
- 开放码2：设置提交时限
- 明确提问：否
- 明确行动请求：是
- 明确时间要求：是
- 提交/分享物：否——当前消息只是请求，还没有提交
- 结果证据：未看到
- local_event_id：E2

### 示例消息 6

原文：“这是第3页。”并附图片

- 事实性概括：发送者提交了第3页图片
- 开放码1：提交图片
- 明确行动请求：否
- 提交/分享物：是
- 出现回应：是
- 结果证据：仅有进展；若图片内容和接收确认都可见，才可标完成
- local_event_id：E2

### 示例消息 7

原文：“收到。”

- 事实性概括：发送者确认收到前文信息
- 开放码1：确认收到
- 出现回应：是
- 结果证据：通常为未看到
- local_event_id：跟随它回应的事项；无法判断时为 UNKNOWN

## 8. `04_事项汇总` 怎么填

一个样本预留5行，不需要全部填满。没有第二个事项时，E2–E5 留空。

以示例 E1 为例：

- 事项中性名称：确认开始时间并进入
- 涉及 rn：例如 `61–63`
- 发起者：使用原表 `sourceuid/昵称`
- 对方被期待提供什么：告知开始时间；随后按要求进入
- 可见推进过程：询问时间 → 告知时间并要求提前进入 → 确认已进入
- 可见结果：完成
- 观察到的摩擦：未观察到
- 缺失上下文：无
- 置信度：高

事项名称仍然不能写成产品功能，例如“智能日程提醒”。

## 9. `05_样本总结` 怎么填

每个样本一行：

- `理解充分性`：整体是否能理解；
- `观察到明确事项`：是否至少有一个 E1–E5；
- `自由主题1–3`：对整个样本的中性概括，例如“询问时间”“请求提交材料”；
- `直接可见事实`：只汇总证据；
- `待验证解释`：可能的场景解释，必须用“可能”表达；
- `需要补充什么`：缺角色、群用途、附件、完整上下文、业务状态等；
- `整体置信度`：对这份样本总结的信心；
- `净室异常`：正常情况保持“无”。

示例：

- 直接可见事实：三条消息围绕开始时间与进入状态展开，最后明确表示已进入；
- 待验证解释：可能与一次课程或活动进入有关，但原表不能证明具体业务对象；
- 需要补充什么：若要确认课程场景，需要独立业务对象字段；
- 自由主题：询问开始时间、确认进入。

## 10. 常见错误清单

1. 看见学科词就标成学习需求；
2. 看见问号就标明确提问；
3. 把“收到”当作任务完成；
4. 把请求提交误标成已经提交；
5. 从昵称、称呼或聊天内容猜老师/学生身份；
6. 只因群里当前都是教师发言就判定为管理群；
7. 用 AI Feature、产品模块或解决方案充当开放码；
8. 为了填满 E1–E5 强行拆事项；
9. 因消息无价值、纯表达或难以理解而跳过；
10. 为了让 A/B 一致而提前对答案。

## 11. 完成前自检

每完成一个样本，检查：

- 20条黄色核心行是否都完成必填项；
- 开放码1是否为事实短语，而不是产品建议；
- 推断警报是否填写，“无”也要明确写出；
- 每条核心行是否有 E1–E5、NONE 或 UNKNOWN；
- 事项汇总是否只使用实际发生的事件行；
- 样本总结是否区分直接事实与待验证解释；
- 没有修改任何灰色原表字段；
- 没有查看另一位标注者结果。

完成后建议另存为：

`原文件名_已完成_标注员代号_日期.xlsx`

不要覆盖最初发放的空白版本。
