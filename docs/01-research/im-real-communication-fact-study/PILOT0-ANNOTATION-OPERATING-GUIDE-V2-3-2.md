# ClassIn IM Pilot 0 v2.3.2 一体化审阅操作指南

> **版本通知（2026-08-30）**：本版的事项层仍包含容易把正常未完成状态误写成问题的“事项关键缺口/备注”。当前审阅请使用 [v2.3.3 字段精简指南](./PILOT0-ANNOTATION-OPERATING-GUIDE-V2-3-3.md)；本文件仅保留审计轨迹。

## 1. 当前状态

v2.3.2 是当前方法与表格可用性审阅版。正式标注仍未开始；等真实 IM 聊天现场和上下文恢复充分后，再由 A/B 两名标注者独立填写。

本版不生成主题比例、需求排序或 IM/AI 产品结论。它只解决人工填表负担和字段歧义。

## 2. 实际填写路径

### 标准互动轨

只填写 `03_逐条开放编码`：

1. 黄色消息层：每条核心消息填写；
2. 绿色事项层：同一事项只在首次出现行填写一次；
3. 紫色样本层：每个 `sample_id` 只在系统标出的唯一紫色核心行填写一次。

`05_样本总结` 是紫色样本层的公式镜像，只用于集中复核。它没有下拉框，不再填写，也不需要人工回查或抄写 `sample_id`、事件 ID、RN、Source ID。

### 单方可见边界轨

`P0-DIR1-01/02` 继续填写 `03` 橙色简化消息字段和 `08_单方可见汇总`，不填写绿色事项层或紫色样本层。

## 3. `00A_填写示例` 怎么看

主要示例表头已直接给出：

- 完整下拉取值或推荐写法；
- Good case；
- Bad case；
- 消息层、事项层和单方边界层的填写差异。

示例消息全部为虚构内容，不属于研究样本，也不构成主题答案。

## 4. 四个容易混淆的字段

### 4.1 本条是否回应前文

只保留三个值：

| 值 | 什么时候选 | 示例 |
| --- | --- | --- |
| `是` | 本条明确回答、确认、拒绝、纠正或补充前文 | 问“几点开始？”后回答“19点” |
| `否` | 本条没有回应前文；包括发起新事项、独立通知、没有可回应前文的首句 | “明天几点开始？”；独立通知第一句 |
| `无法判断` | 消息明显承接其他内容，但关键前文在窗口外或缺失 | 第一条可见消息是“还是不行”，但看不到对象 |

原 `不适用` 已并入 `否`。首句和独立发起可由消息位置与事项结构识别，没有必要再增加一个人工选项。

### 4.2 时效要求

只保留三个值：

| 值 | 什么时候选 | 示例 |
| --- | --- | --- |
| `明确时限` | 有具体日期、时点、时段或截止边界 | “今晚8点前提交” |
| `模糊时效` | 有加快或紧迫表达，但没有具体截止点 | “请尽快提交”“抓紧发来” |
| `未见时效` | 当前可见内容没有出现明确或模糊时效表达 | “请把作业发给我” |

原 `无法判断` 已删除。载荷缺失或正文不可解析，由“可理解程度”和“证据边界/推断警报”记录，不在时效字段重复表达。

### 4.3 证据边界/推断警报

它不评价用户行为好坏，而是提醒：当前判断是否可能越过可见证据。

推荐写法：

- `无`；
- `附件未核验`；
- `关键前文缺失`；
- `角色关系未确认`；
- `窗口外结果不可见`；
- 其他具体、可核查的证据缺口。

Good case：消息有图片占位，但看不到图片内容，写“附件未核验”。

Bad case：写“对方故意不回”“学生不认真”。这些是动机或态度推断，不是证据边界。

### 4.4 本条提供的结果证据

这是消息层字段，判断“本条消息是否提供了事项结果证据”，不是判断整段会话最终有没有结果。

| 值 | 什么时候选 | 示例 |
| --- | --- | --- |
| `完成` | 本条直接出现目标已经达成的证据 | “我已经提交完成了” |
| `受阻` | 本条明确出现失败、拒绝、权限问题或其他障碍 | “上传失败了”“我没有权限” |
| `仅有进展` | 本条显示正在处理或完成了中间步骤 | “正在上传”“先发了第一页” |
| `未看到` | 事项可以识别，但本条没有提供结果证据 | 提出请求、告知安排、普通确认 |
| `无法判断` | 连事项或结果类型都无法识别 | 载荷和关键前后文都缺失 |

因此，大量清楚的请求或告知可能选 `未看到`，但不应为了省事大量选择 `无法判断`。

事项层的“事项可见状态”则要读完整个当前可见事项链后再判断。

## 5. 角色上下文规则继续有效

- `strtalker + sourceuid` 用于区分谁在说话；
- `user_type` 是当前消息的原表角色背景；
- `msgdata.strTalker` 只作显示名校验；
- 不把单条消息的 `user_type` 固化为该用户的全局永久身份；
- 不从昵称猜测老师、学生或关系。

## 6. 完成一个标准样本的最小检查

1. 已先读完同一 `sample_id` 的灰色上下文和核心消息；
2. 黄色核心消息字段已按可见证据填写；
3. 同一事项沿用同一 `E1/E2…`；
4. 每个事项只在首次出现行填写一次绿色字段；
5. 唯一紫色行完成一次样本总结；
6. `05` 能自动显示紫色行内容，且没有在 `05` 重复填写；
7. 不确定规则进入 `06_字段问题`，不靠猜测补齐。
